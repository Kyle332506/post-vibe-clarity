# Support and reporting routes

PostVibeClarity keeps ordinary support, product defects, compatibility evidence, security reports, and conduct concerns on separate paths. Read the [README](README.md) and the applicable installation guide before opening a report, and keep reports factual, reproducible, and free of secrets.

| Need | Route |
| --- | --- |
| Usage question | Read the installation guides first. Use a GitHub issue with the bug form only when the observed behavior is defective. |
| Product defect | Use the Bug report form. Include the expected behavior, actual behavior, steps to reproduce, version, and sanitized evidence. |
| Agent compatibility result | Use the Agent compatibility form. Include the agent, version, installation path, invocation, date, and observed result. |
| Security vulnerability | Submit a private vulnerability report as described in [SECURITY.md](SECURITY.md); never create a public issue. |
| Conduct concern | Use the private contact method listed on the maintainer's GitHub profile, as described in [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). |

## Before reporting a defect

Confirm that the behavior is reproducible with a supported version and that the report does not contain credentials, tokens, private keys, personal data, or project material you cannot share. A minimal repository or sanitized command output is usually more useful than a broad claim about readiness or security.

## Report expectations

Reports should describe the evidence available and the uncertainty that remains. The maintainers may ask for clarification or a smaller reproduction. A report is not a certification that a project is production-ready, secure, compliant, or defect-free; review [DISCLAIMER.md](DISCLAIMER.md) for the complete boundary.
